# 점수 시스템 네이티브 1953점 재설계

## 배경 / 문제

현재 점수 표시는 "백엔드 100점 만점 → 화면 1953점 환산"으로 알려져 있었지만, 실제 코드(`gookbapgame/app/lib/stageConfig.ts`)를 확인해보니 백엔드에 저장되는 점수 자체가 없다. `game_score_logs`에 아직 아무것도 쓰지 않고(점수 제출은 별도 후속 스펙 범위, `2026-07-30-player-identity-design.md` 참고), 실제로는 클라이언트 메모리 안에서 레벨 배점+보너스를 단순히 더한 raw 합계(2040+100+400+53=2593)를 0~100 비율로 낮췄다가 다시 1953으로 올리는 2-pass 환산이 표시 직전에 일어날 뿐이다.

반면 `gookbapanalyze`의 `gatcha_cases` 테이블은 이미 `CHECK (max_score <= 1953)`로 1953 스케일을 전제하고 있어(`gookbapanalyze/AGENTS.md`), 클라이언트가 계산 도중에만 100점 비율을 거치는 현재 구조와 방향이 어긋나 있다. 점수 제출 기능 자체가 아직 미구현이라 지금이 이 2-pass 환산을 걷어내고 **처음부터 0~1953 스케일로 계산**하도록 바꿀 수 있는 시점이다.

이와 별개로 최근 팀 회의에서 게임 규칙 자체도 재설계됐다(레벨 수 축소, 전체 제한시간제, 레벨당 오답 횟수 제한). 이 스펙은 두 변경을 함께 다룬다: (1) 환산 없이 네이티브 1953점으로 계산하는 구조로 전환, (2) 새 게임 규칙에 맞는 배점 체계 설계.

**범위**: 클라이언트(`gookbapgame`)의 점수 계산 로직과 그에 필요한 게임 규칙 변경. `game_score_logs`에 실제로 점수를 기록하는 제출 로직(부정 참여 방지용 실시간 DB 대조 포함)은 여전히 후속 스펙 범위다 — 다만 이 스펙에서 나오는 최종 값이 이미 1953 스케일이므로 그 스펙에서 추가 환산이 필요 없다.

## 게임 규칙 변경

- **레벨 수**: 9 → **7**. DB 스키마(`STAGE_CONFIG` 대응 구조)는 9자리를 마련해뒀지만 실제 기획은 7단계였다.
- **제한시간**: 레벨별 60초(총 540초, 레벨마다 개별 카운트다운) → **전체 300초(5분) 단일 타이머**로 교체. 게임 시작 시 한 번 시작해 7레벨을 모두 클리어(또는 강제종료)할 때까지 흐른다. 300초를 다 쓰면 그 시점에서 즉시 게임을 종료한다.
- **오답 처리(신규)**: 레벨당 오답 3회까지 허용. 4번째 오답(3회 소진) 시점에 그 레벨에서 못 찾은 정답은 포기하고 즉시 다음 레벨로 강제 이동한다.

## 점수 구성 (총점 1953)

| 항목 | 만점 | 비중 |
|---|---|---|
| 스테이지 점수 | 800 | 41.0% |
| 시간 보너스 | 600 | 30.7% |
| 콤보 보너스 | 553 | 28.3% |
| **합계** | **1953** | 100% |

### 스테이지 점수 (800점)

레벨별 고정 배점 풀을 두고, 그 판에서 실제로 요구된 정답 개수(diffCount — 콘텐츠 분량/관리자 설정에 따라 판마다 달라짐)로 나눠 "정답 1개당 점수"를 계산한다. 정답을 찾을 때마다 그 값만큼 가산되고, 못 찾은 정답은 자연히 못 받는다 — 별도 감점 없이 이 간접 페널티로 충분하다.

| 레벨 | 배점 |
|---|---|
| 1 | 50 |
| 2 | 50 |
| 3 | 100 |
| 4 | 100 |
| 5 | 150 |
| 6 | 150 |
| 7 | 200 |
| **합계** | **800** |

`정답 1개당 점수 = 레벨 배점 ÷ 그 레벨의 실제 diffCount`. 계산은 내부적으로 float로 유지하고, 반올림은 최종 총점을 화면에 표시할 때 **한 번만** 적용한다(중간 단계마다 반올림하지 않는다).

### 시간 보너스 (600점)

"총 플레이 시간"(첫 레벨 시작 ~ 마지막 레벨 클리어 또는 강제종료 시점까지)과 "정답률"(이번 판에서 실제로 찾은 정답 수 ÷ 이번 판 전체 정답 수) 두 값으로 결정된다.

1. 정답률로 기준 점수(티어)를 정한다:

   | 정답률 | 티어 점수 |
   |---|---|
   | 0~20% | 0 |
   | 21~40% | 50 |
   | 41~60% | 100 |
   | 61~80% | 200 |
   | 81~90% | 400 |
   | 91~100% | 600 |

2. 100초 이내에 완주했으면 시간 보너스 = 티어 점수 그대로.
3. 100초를 넘겼으면, 넘긴 시간을 10초 단위로 끊어 구간마다 티어 점수에서 30점씩 뺀다:

   `시간 보너스 = max(0, 티어 점수 − 30 × ceil((경과시간 − 100) ÷ 10))`

   0 밑으로는 내려가지 않고(클램프), 이 계산은 시간 보너스 항목 안에서만 끝나며 다른 점수 항목에 영향을 주지 않는다.
4. 300초를 넘기면 강제종료된다(아래 "미완주 감점" 참고).

예시(정답률 91~100% 티어, 티어 점수 600 기준): 100초=600, 105초=570, 115초=540, ... 300초에 가까워질수록 0에 수렴한다(`ceil` 계산상 정확히 0이 되는 시점은 291초부터). 정답률이 낮으면(예: 61~80%, 티어 200) 100초 초과 시 더 빨리 0에 도달한다(200÷30 ≈ 6.67구간이므로 161초부터 이미 0).

이 설계의 핵심 의도: 정답률이 낮은 플레이어는 시간 보너스의 "출발점"과 "버틸 수 있는 구간" 모두 줄어든다 — 정답률 0%면 몇 초에 끝내든 시간 보너스가 항상 0이 되어, 아래 "검증된 엣지 케이스"의 악용을 원천 차단한다.

### 콤보 보너스 (553점)

오답 없이 이어지는 연속 정답 스트릭에 비례해 실시간으로 누적되는 점수. 레벨 경계와 무관하게 게임 전체(7레벨) 단위로 하나의 스트릭 카운터를 쓴다.

`그 순간까지의 콤보 점수 = 553 × (현재 스트릭 길이 ÷ 이번 판 전체 정답 수 N)²`

- N(이번 판 전체 정답 수)은 `preloadAllStages`가 7레벨 세션을 게임 시작 전에 모두 fetch해두므로(`preloadGame.ts:35-37`) 1레벨 시작 시점에 이미 확정돼 있다 — 실시간 라이브 표시가 가능하다.
- 오답이 발생하면: 그 순간까지 쌓인 콤보 점수는 그대로 총점에 남고(적립분 보존), 스트릭 카운터만 0으로 리셋된다. 이후 위 공식으로 처음부터 다시 쌓기 시작한다.
- 특성: 오답이 균등한 간격으로 k회 발생하면 최종 콤보 총점은 약 `553 ÷ (k+1)`로 수렴한다. 오답 단 1회로 콤보 만점의 절반가량(≈276.5점)이 날아가는 급격한 곡선이며, "무결점 완주에게만 파격적으로 보상한다"는 의도된 설계다. 스트릭이 길어질수록(즉 후반부일수록) 오답 1회의 손실폭이 커지는 비대칭 구조이기도 하다 — 초반 실수보다 막판 실수가 더 아프다.

## 감점 항목

| 항목 | 크기 | 적용 시점 |
|---|---|---|
| 오답 직접 감점 | 오답 1회당 -10점 | 발생 즉시 |
| 미완주 감점 | 아예 시작 못 한 레벨 1개당 -10점(최대 -70점, 7레벨 기준) | 300초 초과로 강제종료될 때 |

- 오답 직접 감점은 스테이지 점수/콤보 점수와 별개로 총점에서 바로 차감된다(간접 페널티인 "못 찾은 정답만큼 못 받음"과는 다른 축).
- 미완주 감점: 300초를 넘겨 강제종료될 때, **그 순간 진행 중이던(머물러 있던) 레벨은 감점 대상에서 제외**한다 — 그때까지 찾은 정답은 스테이지 점수로 그대로 인정하고, 그 이후로 아예 시작조차 못 한 레벨만 카운트해서 감점한다.
- 모든 감점을 반영한 후 총점이 음수가 되면 화면엔 0점으로 표시한다(마이너스 노출 안 함).

## 검증된 엣지 케이스 (악용 방지)

"오답 3회를 일부러 다 써서 정답을 찾으려 하지 않고 7레벨을 최대한 빠르게 강제 스킵" 전략을 검증했다:

- 정답률 0% → 스테이지 점수 0, 콤보 점수 0, **시간 보너스도 티어 점수가 0이라 몇 초에 끝내든 0**(시간 보너스 공식에서 티어가 0이면 어떤 경과시간에도 `max(0, 0 − 30n) = 0`).
- 오답 감점만 7레벨 × 3회 × -10점 = -210점.
- 총점 = 0 + 0 + 0 − 210 → 음수이므로 화면엔 0점.
- 결론: 이 전략은 순수하게 손해이며, 정직하게 플레이하는 것보다 나은 결과를 주지 않는다.

- **`app/lib/stageConfig.ts`**: 전면 재작성.
  - 삭제: `timeLimitSec`(레벨별 타이머), `MAX_TIME_BONUS`, `TIME_BONUS_TARGET_RATIO`, `COMPLETION_BONUS`, `STREAK_BONUS`, `calcStreakBonus`, `RAW_MAX_SCORE`, `DISPLAY_MAX_SCORE`, `toDisplayScore`, 그리고 `calcFinalScore`의 0~100 비율 환산 로직 전체.
  - 신규: `STAGE_CONFIG`를 7레벨(레벨별 고정 배점 필드 포함)로 축소, `GLOBAL_TIME_LIMIT_SEC = 300`, `WRONG_TOUCH_LIMIT_PER_LEVEL = 3`, `WRONG_TOUCH_PENALTY = 10`, `INCOMPLETE_LEVEL_PENALTY = 10`, `COMBO_BONUS_MAX = 553`, `TIME_BONUS_MAX = 600`, `TIME_BONUS_FAST_THRESHOLD_SEC = 100`, `TIME_BONUS_STEP_SEC = 10`, `TIME_BONUS_STEP_VALUE = 30`, 정답률 6단계 티어 테이블. 최종적으로 0~1953 정수(반올림 1회)를 반환하는 `calcFinalScore()`로 통합.
  - `GUKBAP_TIER_CUTOFFS`: 새 만점 구조(스테이지 800 상한 등)에 맞춰 재설계 필요 — 정확한 컷오프 값은 밸런스 테스트 후 확정.
- **`app/hooks/useGameProgress.ts`**: 레벨별 `remainingTimeByStage` 배열 대신 게임 전체를 관통하는 단일 타이머 state 필요. `hadWrongTouch: boolean` 대신 (a) 레벨당 오답 횟수 카운터, (b) 게임 전체 콤보 스트릭 카운터, (c) 콤보 누적 점수(실시간 표시용)로 교체. `advanceToNextStage`에 "오답 3회 소진 시 강제 진행" 트리거 추가.
- **`app/components/GameScreen.tsx`**: `handleSlotClick`의 오답 분기(`onWrongTouch()`)에 레벨별 카운트 로직과 3회 소진 시 강제 다음 레벨 이동을 연결해야 한다.
- **`app/components/GameResultScreen.tsx`, `DailyResultScreen.tsx`**: `toDisplayScore()` 호출을 제거하고 `calcFinalScore()`가 반환하는 최종 1953 스케일 값을 그대로 사용한다.
- **`app/lib/preloadGame.ts`**: `STAGE_CONFIG` 타입 변경에 맞춰 `fetchSession` 호출부 필드명만 조정(전체 세션을 미리 fetch하는 로직 자체는 변경 불필요 — 콤보 분모 N을 게임 시작 전에 확정할 수 있는 이유이기도 하다).

## 리스크 / 확인 필요 사항

- **`diffCount`(목표 정답 개수)의 관리자 대시보드 연동 여부 미확인**: 현재 코드(`stageConfig.ts`)는 레벨별 목표 diffCount가 하드코딩돼 있고, 실제 판마다의 diffCount는 콘텐츠 부족 시에만 그 아래로 축소된다(`actions.ts`의 `clampDifferenceCount`). 관리자가 대시보드에서 목표치 자체를 유동적으로 바꿀 수 있는 별도 채널이 있는지는 이번 조사에서 찾지 못했다 — 다만 이 스펙의 "고정 배점 풀 ÷ 실제 diffCount" 방식은 목표치가 어디서 오든(하드코딩이든 대시보드 설정이든) 실제 런타임 diffCount만 알면 그대로 동작하므로 이 스펙 자체의 정합성엔 영향 없음. 구현 착수 전 확인 권장.
- **등급 컷오프(`GUKBAP_TIER_CUTOFFS`) 미확정**: 스테이지 800 / 시간 600 / 콤보 553이라는 새 구조에서 어떤 조합이 어떤 등급에 해당해야 자연스러운지는 실제 플레이 데이터 없이 확정하기 어렵다. 밸런스 테스트 후 별도로 정한다.
- **`gookbapanalyze`의 `gatcha_cases.max_score` 구간 설정**: 기존 점수 분포(2-pass 환산 결과) 기준으로 구간이 잡혀 있었다면, 이번 재설계로 "일반적으로 도달 가능한 점수대"가 달라질 수 있다(특히 콤보 비중이 커서 오답 1회만 나도 총점이 크게 흔들린다). 구자건에게 새 스코어 분포를 공유하고 가챠 구간 재검토를 요청해야 한다.
- **콤보 공식의 순서 의존성**: `553 × (스트릭/N)²`의 "균등 간격 오답 k회 → 총점 553/(k+1)" 근사는 오답이 고르게 퍼졌을 때의 값이다. 실제로는 스트릭이 길어질수록(후반부일수록) 오답 1회의 손실폭이 커지므로, 오답이 초반에 몰리는 경우와 후반에 몰리는 경우 최종 콤보 점수가 달라진다. 의도된 비대칭이지만 플레이어에게 이 사실이 잘 전달되도록 결과 화면 UX에서 안내가 필요할 수 있다.

## 범위 밖 (후속 스펙)

- `game_score_logs`에 실제로 점수를 기록/제출하는 로직(부정 참여 방지를 위한 스테이지 단위 실시간 DB 대조 포함, `~/.agents/memory/project_gookbapgame_anticheat_direction.md` 참고). 이 스펙에서 계산되는 최종 값은 이미 0~1953 스케일이므로, 후속 스펙에서 별도 환산 없이 그대로 저장하면 된다.
- 가챠(`/api/gatcha/draw`) 확률 구간(`gatcha_cases.max_score`) 재조정 — `gookbapanalyze`/구자건 담당.
- 등급 컷오프(`GUKBAP_TIER_CUTOFFS`), 레벨별 정확한 diffCount 목표치의 대시보드 연동 여부, 콤보/시간 보너스 세부 상수의 최종 밸런스 확정 — 실 플레이 테스트 이후 진행.
