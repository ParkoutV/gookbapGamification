# 서버 측 이미지 합성 + 캐시 설계

## 배경 / 문제

다른그림찾기 게임은 배경 이미지 위에 슬롯별 파츠 이미지를 겹쳐 좌/우 화면을 구성한다. 현재 `GameScreen.tsx`는 배경 1장 + 슬롯 N개 × 2(좌우)의 개별 `<img>` 태그를 렌더링한다. 각 이미지가 개별 네트워크 요청으로 순차 로딩되면서, 유저가 파츠들이 하나씩 나타나는 "조립 과정"을 그대로 보게 된다. 이는 마케팅 목적의 불특정 다수 대상 게임에서 UX를 해치고 정답 유추의 단서가 될 수 있다.

DB 스키마(`base_images` / `part_categories` / `parts` / `image_slots`)는 파츠 단위로 정규화되어 있으며, 이는 관리자 대시보드(`gookbapanalyze`)의 편집 기능과 향후 파츠 확장성을 위해 유지되어야 한다. 즉 문제는 스키마가 아니라 **클라이언트에 전달되는 시점의 표현 방식**에 있다.

## 해결 방향

서버 측에서 배경+파츠를 픽셀 단위로 합성한 완성 이미지를 만들고, 동일한 조합이 재요청되면 캐시된 이미지를 재사용한다. 사전에 모든 조합을 생성하지 않고(조합 폭발 방지), 실제로 플레이된 조합만 요청 시점에 지연 생성한다.

### 왜 이 방향인가 (대안 비교)

- **클라이언트 Canvas 합성**: 서버 부하는 없지만, 파츠 이미지 자체를 클라이언트로 내려보내야 하므로 "정답 유추 가능한 원본 데이터가 클라이언트에 존재"하는 근본 문제가 남는다.
- **사전 전량 합성**: 파츠 조합이 카테고리당 여러 개일 경우 조합 수가 급격히 늘어나 낭비. 실제 플레이 분포와 무관하게 저장 비용 발생.
- **채택안(지연 합성 + 캐시)**: 클라이언트는 완성 이미지 URL만 받음(정답 유추 불가), 조합 생성은 실제 요청된 만큼만 발생, 재접속·재플레이 시 캐시 히트로 sharp 연산 생략.

## 아키텍처

### 데이터 흐름

1. `fetchGameData` (서버 액션)가 기존 로직대로 base_image + 유효 슬롯 + 파츠 후보를 조회하고, 슬롯별로 좌/우에 어떤 `part`를 쓸지 무작위로 결정한다 (현재 로직 유지).
2. 결정된 조합을 캐시 키로 직렬화한다: `base_image_id` + 좌/우 각각 정렬된 `[slotId:partId]` 목록 → SHA-256 해시.
3. Supabase Storage `game_assets` 버킷의 `cache/composed/<hash>.webp` 존재 여부를 확인한다.
   - **존재**: 해당 public URL을 즉시 사용.
   - **부재**: `sharp`로 배경 이미지 위에 각 파츠를 슬롯 좌표·오프셋·스케일에 맞춰 합성 → WebP 인코딩 → Storage 업로드 → public URL 획득.
4. 좌/우 각각 완성된 이미지 URL과, 정답 판정에 필요한 슬롯 메타데이터(`slotId`, `x`, `y`, `slotScale`, `isDifference`)만 클라이언트로 반환. 파츠 개별 이미지 URL은 더 이상 클라이언트로 보내지 않는다.
5. 클라이언트(`GameScreen.tsx`)는 좌/우 `<img>` 2장만 렌더링하고, 그 위에 슬롯 좌표 기준 투명 클릭 오버레이(현재의 `handlePartClick` 판정 영역)만 얹는다.

### 캐시 미스 시 UX

기존 `StartScreen`의 `isLoading` 상태를 그대로 사용한다. `fetchGameData` 서버 액션 내부에서 합성+업로드까지 끝난 뒤 결과를 반환하므로, 클라이언트 입장에서는 "로딩 중..." 문구가 조금 더 길게 보일 뿐 별도 UI 변경이 필요 없다.

### 변경 범위

- **변경**: `app/actions.ts` (합성/캐시 로직 추가, 반환 타입 축소), `app/components/GameScreen.tsx` (파츠별 오버레이 렌더링 제거 → 완성 이미지 2장 + 투명 클릭 영역)
- **불변**: Supabase 테이블 스키마, RLS 정책, `gookbapanalyze` 대시보드, `StartScreen.tsx`, `Modal.tsx`, `page.tsx`의 상태머신

## 미해결 리스크 — Storage 업로드 권한

`gookbapanalyze/AGENTS.md`에 따르면 프론트엔드는 `ANON_KEY`만 사용해야 하며, 현재까지 `game_assets` 버킷 업로드는 전부 로그인된 관리자(`gookbapanalyze`)에서만 이루어졌다. anon 역할이 이 버킷에 INSERT 가능한지는 미확인 상태.

- 확인 필요: Supabase Storage 버킷 정책(RLS)에서 `cache/composed/` 경로에 대한 anon INSERT 허용 여부.
- 막힐 경우 대응: `AGENTS.md` 원칙(SERVICE_ROLE_KEY 우회 금지)에 따라, 임의 우회 대신 팀원과 버킷 정책 조정을 논의하거나 `SECURITY DEFINER` RPC 함수를 통한 업로드 경로를 검토한다.
- 로컬 검증 환경이 아직 없으므로(`.env`/`db.properties` 미설정), 실제 Supabase 프로젝트 연결 전까지는 sharp 합성 로직만 순수 함수 단위로 검증하고, Storage 연동은 연결 확인 후 진행한다. 연결이 끝내 불가능하면 로컬 더미 데이터로 로직만 검증한다.

## UI 톤앤매너

팀 회의에서 확정된 디자인 방향은 없음. "캐주얼한 콘솔 게임" 느낌이라는 방향성만 있고, 세부 비주얼은 구현 단계에서 별도로 디벨롭한다. 이 스펙은 이미지 합성/캐시 아키텍처에 한정하며, 비주얼 디자인은 범위에서 제외한다.

## 테스트

- sharp 합성 함수: 고정된 배경+파츠 좌표 입력에 대해 출력 이미지 크기/포맷이 기대값과 일치하는지 확인하는 최소 스모크 테스트.
- 캐시 키 함수: 동일 조합 → 동일 해시, 다른 조합(파츠 순서 변경 포함) → 다른 해시가 아님(정렬 후 동일)을 확인하는 단위 테스트.
