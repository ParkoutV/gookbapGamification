# 비주얼 아이덴티티 리뉴얼 설계

## 배경 / 문제

`2026-07-21-frontend-core-flow-redesign-design.md`는 "비주얼 톤앤매너(색상/폰트/브랜드 그래픽)"를 명시적으로 범위 밖에 두고 기존 다크톤 레이아웃을 그대로 유지했다. 그 결과 현재 UI(`StartScreen`, `StageTransitionModal`, `GameResultScreen` 등)는 보라-핑크 그라디언트 + `backdrop-blur` 글래스모피즘으로, 별도 디자인 검토 없이 만들어진 Next.js 템플릿 수준의 스타일이다. 게임의 실제 소재(국밥 한 상차림)와 아무 관련이 없다.

최근 하이파이 픽셀아트로 그린 국밥 상차림 레퍼런스 이미지(나무 소반, 스텐 그릇, 뚝배기, 반찬 — 회색 배경)가 나왔고, 이를 게임 전체 비주얼 컨셉의 기준으로 삼기로 했다. 이번 스펙은 이 레퍼런스를 기준으로 한 시각적 언어(컬러/타이포/컴포넌트 스타일)를 정의하고, 기존 6개 화면(`StartScreen`, `GameScreen`, `WheelScreen`, `StageTransitionModal`, `GameResultScreen`, `DailyResultScreen`)에 적용하는 방향을 정한다.

## 범위

### 이번 스펙에서 다루는 것

- 컬러/타이포 토큰 시스템 정의
- 카드·버튼 등 공용 컴포넌트의 코너/테두리 처리 기법 (SVG 마스크 기반)
- 6개 기존 화면에 토큰을 적용하는 방향 (레이아웃 구조 변경 없이 스타일만 교체)
- 픽셀아트 히어로 이미지 사용 규칙

### 다음으로 이관 (명시적 제외)

- 룰렛(WheelScreen) 자체의 그래픽/애니메이션 — 원형 UI라 계단 코너 기법이 그대로 안 맞음. 별도 에셋 제작이 필요하며 이번 스펙은 룰렛을 감싸는 카드/버튼에만 토큰을 적용한다.
- 국밥력 티어별 "도장(스탬프) 배지" 일러스트 — 브레인스토밍 중 방향(C안)으로 제안했으나 이번 스펙 범위 밖. 결과화면에 나중에 얹어도 현재 방향과 충돌하지 않는다.
- `mask-composite`의 실제 크로스브라우저 동작 검증(Safari `-webkit-mask-composite` 키워드 값 확정 등) — 구현 단계에서 caniuse/실기기로 확인.
- 다크 모드 — 이 UI는 따뜻한 종이·나무 톤에 의도적으로 고정된 단일 테마로 간다. OS 다크 모드 대응은 이번 스펙 범위 밖.

### 타이포그래피

- 본문/버튼/UI 전반: 깔끔한 산세리프(Pretendard 계열). 미니멀 플랫 기조를 유지한다.
- 픽셀(도트) 폰트는 딱 두 곳에만 제한적으로 사용한다: 게임 로고 타이틀, 그리고 결과 화면의 큰 점수/국밥력 숫자(예: "1953"). 전체를 도트체로 바르면 UI가 산만해진다.

## 컴포넌트 스타일

- **버튼**: 완전한 라운드 필 대신 얕은 2단 계단(픽셀 노치) 코너.
- **카드/패널**: 그림자 대신 얇은 나무색 테두리 + 계단 코너. 기존 `backdrop-blur` 글래스모피즘은 전부 제거한다.
- **아이콘**: 이모지(🔄 등) 대신 레퍼런스 이미지 속 실제 오브젝트(수저, 그릇)를 단순화한 단색 라인 아이콘으로 통일.
- **여백**: 소반 위 그릇 배치처럼 카드 사이 간격을 넉넉하게 둔다.
- **로딩/에러 상태**: 기존 텍스트 그대로 유지, 색상만 토큰 반영(에러는 위 표의 시맨틱 에러 컬러, 로딩은 `--amber` 계열).

### 코너 처리 기법 (중요 — 구현 시 그대로 따를 것)

브레인스토밍 중 세 가지 실패/개선을 거쳐 아래 방식으로 확정했다. 각 단계에서 왜 앞 단계가 안 됐는지 남겨둔다.

1. **`clip-path: polygon()`으로 계단 코너를 표현하는 것 자체는 동작한다.** 단, 카드/버튼처럼 바깥 테두리 색 + 안쪽 배경색의 "이중 레이어" 구조를 쓸 때, **바깥/안쪽 레이어에 서로 다른(손으로 축소 계산한) 폴리곤 좌표를 쓰면 두 계단이 안 맞물려서 테두리가 끊긴다.** 대신 **완전히 동일한 폴리곤을 바깥/안쪽에 그대로 재사용**하고, 테두리 두께는 오직 바깥 요소의 `padding` 값으로만 결정해야 한다. 모든 변이 수평/수직인 계단 도형이라, 이렇게 하면 균일한 padding 두께의 띠가 자동으로 생긴다.
2. **`clip-path`는 앨리어싱(안티에일리어싱)을 완전히 끄는 것을 보장하지 않는다.** 브라우저가 클립 마스크를 래스터라이즈할 때 기본적으로 안티에일리어싱을 적용하고, SVG의 `shape-rendering: crispEdges` 같은 힌트가 `clip-path`에는 적용되지 않는다.
3. **최종 채택: SVG `<mask>` + `shape-rendering="crispEdges"`를 `mask-image`로 적용.** 마스크(폴리곤)는 색이 없는 순수 형태(알파/명도)만 담당하고, 실제로 보이는 색은 요소의 `background`(=CSS 토큰)에서 가져온다 — 이러면 나중에 토큰 색을 바꿔도 마스크 이미지를 다시 만들 필요가 없다. `border-image`처럼 이미지 자체에 색을 구워넣는 방식은 토큰 체계와 단절되므로 쓰지 않는다.
4. **반응형 대응**: SVG `points`는 퍼센트를 못 쓰기 때문에 `clip-path`의 `calc(100% - Npx)` 같은 "카드는 크게, 코너는 고정 픽셀"을 그대로는 못 쓴다. 목표 구현은: 전체 사각형을 100%로 늘어나는 완전 가시(흰색) 베이스 마스크로 깔고, 모서리 4곳에만 고정 픽셀 크기(예: 12×12)의 계단 노치 마스크를 `mask-composite: subtract`로 얹어 깎아낸다. 이러면 가장자리/중앙은 요소 크기에 맞춰 늘어나고, 모서리만 항상 고정 픽셀로 유지된다.
5. **크로스브라우저**: `mask-composite`(표준, Firefox/Chromium)와 `-webkit-mask-composite`(Safari — `subtract`가 아니라 `destination-out` 같은 Porter-Duff 키워드 사용) 둘 다 병기한다. 정확한 지원 버전/키워드는 구현 시 caniuse로 재확인한다.
6. **코너 크기**: 실측 비교 결과 "얕게" 스케일을 채택 — 카드류는 2단 계단 1.5px/2.5px/6px, 버튼류는 1px/1.5px/4px.
7. **에셋 포맷**: 이 코너 마스크는 기하학적 도형이라 SVG(벡터, 텍스트 기반)로 만든다 — 압축된 WebP보다도 가볍다. 반면 실사/텍스처성 에셋(히어로 국밥 이미지, 다른그림찾기 실제 게임 이미지)은 기존처럼 WebP를 유지한다. "PNG냐 WebP냐"는 마스크에는 해당하지 않는 선택지다.
8. **성능**: `clip-path`/마스크 모두 요소가 리사이즈될 때만 마스크를 다시 래스터라이즈한다 — `transform`/`opacity` 애니메이션은 영향받지 않는다. 이번 스펙 범위(카드 1개, 버튼 몇 개, 모달)는 개수가 적고 크기 애니메이션도 없어 성능 이슈가 없다. 나중에 랭킹 리스트처럼 같은 계단 코너를 수십~수백 개 반복·스크롤하는 화면이 생기면 그때 재검토한다(라운드나 래스터 에셋으로 대체 고려).

## 화면별 적용

| 화면 | 적용 방향 |
|---|---|
| `StartScreen` | 카드 하나(로고 + 환영 문구 + 시작 버튼 + 보조 버튼 2개), 배경은 `--bg` 단색. 국밥력 티어는 이름 옆에 `--amber` 텍스트로 상시 노출 |
| `GameScreen` | 다른그림찾기 이미지 두 장이 화면 대부분을 차지하므로 UI 크롬은 최소화 — 상단 얇은 바(타이머·스테이지 표시)만 카드 톤 유지. 배경은 이미지와 대비를 위해 `--bg`보다 살짝 어둡게 |
| `StageTransitionModal` | 블러 오버레이 대신 계단 코너 카드를 화면 중앙에, 배경은 우드톤 반투명(기존 검정 반투명 대체) |
| `GameResultScreen` / `DailyResultScreen` | 점수·국밥력 티어에만 픽셀 폰트를 크게 사용(예: "1953", "국밥 단골"). 나머지 텍스트/버튼은 동일 토큰 |
| `WheelScreen` | 휠 자체 그래픽은 범위 밖(위 "다음으로 이관" 참조). 휠을 감싸는 카드/버튼은 동일 토큰 적용 |

## 열린 질문 / 리스크

- 에러 상태 시맨틱 컬러의 정확한 값 — 구현 시 접근성 대비(WCAG) 확인 후 확정.
- `mask-composite` 서브트랙트 방식의 실제 크로스브라우저 동작은 아직 라이브로 검증하지 않았다(고정 크기 데모로만 SVG mask + crispEdges 자체의 크리스프함/토큰 분리만 검증함). 구현 착수 전 실기기/캔유즈 확인 필요.
