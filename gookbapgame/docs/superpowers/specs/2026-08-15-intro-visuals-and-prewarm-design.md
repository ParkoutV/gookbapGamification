## 1. 데이터 프리워밍

### 문제

`fetchGameData`는 레벨 하나당 **순차 왕복이 5~6번**이다.

```
base_images → image_slots → parts   (앞 결과가 있어야 다음 쿼리를 짠다)
→ part_categories
→ 합성 API 좌/우 2번
```

7레벨이 병렬이므로 전체 지연은 이 한 줄만큼이다. **페이로드는 몇 KB인데 왕복이 병목이다** —
매장 네트워크에서 왕복 1회가 200ms면 그것만으로 1초를 넘는다.

그동안 시작 화면 체류 시간(언어 선택·약관·닉네임 확인)은 그냥 버려진다.

### 처방

첫 상호작용 시점에 **세션 데이터만** 미리 받아 ref에 담아둔다. 이미지 14장 다운로드는
포함하지 않는다.

### 트리거를 마운트가 아니라 첫 상호작용에 거는 이유

`fetchGameData`의 마지막이 합성 API 호출인데, 그 엔드포인트는 캐시에 없으면
**sharp로 이미지를 만들고 Storage에 업로드한다**(`gookbapanalyze`의
`generate-unified/route.ts` 142·150행 실물 확인). 마운트에 걸면 **시작 화면만 보고
나가는 사람에게도 서버 합성 14건**이 발생한다.

첫 상호작용을 한 사람은 그냥 착지한 사람보다 플레이할 확률이 훨씬 높고, 노리는 체류
시간도 대부분 그 이후다. `useButtonClickSfx`가 첫 pointerdown을 잡는 것과 같은 이유다.

> 참고: 캐시 키는 `(baseImageId, imageSlots)` 정확 일치다. 파츠가 카테고리당 2개면
> 배경 한 장의 조합 수가 수십~수백 가지라 실사용에서 캐시가 금방 찬다. 다만 **실제
> 히트율은 프로덕션 데이터 없이 측정 불가**다.

### 반드시 지킬 규칙 — ref 격리

**프리워밍은 자기 ref에만 쓴다. `preloadStatus`·`sessions`·`loadError`·`phase`를
절대 건드리지 않는다.**

이 규칙 하나가 셋을 동시에 막는다.

1. **시작 안 눌렀는데 게임이 시작되는 사고** — 프리로드 완료는 게임 진입의 방아쇠다
   (`page.tsx:137`이 "runPreload를 부르지 않는다"고 경고하는 이유, `useGameProgress:49` 참고).
2. **`preloadStatus`/`loadError` 불변식** — 두 값은 항상 함께 성립해야 하며 서로 다른
   화면이 각각을 근거로 같은 에러 UI를 켠다(`useGameProgress:225` 주석).
3. **`game_start` KPI 정의** — `phase → "playing"` 전이에 걸려 있다. 이 전이를 건드리면
   대시보드 수치가 이유 없이 바뀐다(AGENTS.md가 명시적으로 금지).

프리워밍 실패는 **조용히 넘긴다.** ref를 비워두면 `startGame`의 정상 경로가 평소처럼
에러를 띄운다 — 에러 표시 자리를 두 곳으로 늘리지 않는다.

### 결과값이 아니라 in-flight 프로미스를 저장한다

프리워밍 도중에 시작을 누르는 경우가 실제로 흔하다. 프로미스를 저장해두면 그때
**진행 중인 작업을 기다릴 뿐 중복 요청이 생기지 않는다.** 이미 끝난 경우도 같은
메커니즘으로 처리된다(resolved promise를 await).

**`preloadGenerationRef` 가드를 우회하지 말 것.** `runPreload`는 세대 번호로 늦게 온
결과가 최신 요청을 덮어쓰는 것을 막는다(`useGameProgress:75` 주석). 프리워밍 프로미스를
await하더라도 **세대 스냅샷과 비교는 `runPreload` 안에, await를 감싸는 위치에 그대로
남아야 한다** — 세션이 어디서 왔든 상관없이. 프리워밍이 resolve되는 사이에 더 새로운
`runPreload`가 시작됐다면 옛 호출은 `setSessions` 전에 빠져나가야 한다.

### 트리거는 기존 pointerdown 리스너에 얹는다

`useButtonClickSfx`가 이미 문서 전역 첫 pointerdown에서 `preloadSfx()`와 `resumeBgm()`을
부른다. **문서 리스너를 하나 더 만들지 말고 거기 얹을 것** — AGENTS.md가 그 자리를
고른 이유("첫 조작이 버튼이라는 보장이 없다")가 프리워밍에도 그대로 적용된다.

### 한 번 쓰고 반드시 비운다

**이걸 빠뜨리면 2026-08-15에 `43252ed`로 막은 중복이 되살아난다.**

프리워밍한 세트를 소비 후에도 남겨두면 '다시하기'가 **같은 세트를 그대로 재생**한다.
배경도 정답 위치도 동일한 판이다. 그 방어(`lastBaseImageIdsRef` + `orderBaseImageCandidates`)는
`fetchGameData`를 새로 부를 때만 작동하므로, 캐시된 세션을 재사용하면 아예 우회된다.

- 소비 즉시 ref를 비운다.
- 시작 화면으로 돌아왔을 때 새로 프리워밍할지는 **선택**이다. 한다면 그 시점의
  `lastBaseImageIdsRef`를 넘겨 직전 판 회피가 걸리게 해야 한다.

### 테스트 이음매

`preloadAllStages`를 둘로 나눈다.

```
fetchAllSessions(fetchSession, lastBaseImageIds)  // 순수, 주입 가능
loadSessionImages(sessions, loadImage)
preloadAllStages = 위 둘의 합성 (기존 시그니처 유지)
```

`preloadGame.test.ts`가 이미 쓰는 방식이라 훅 인프라 없이 검사할 수 있다.

검사할 것:
- 프리워밍한 세션은 **정확히 한 번만** 소비된다(두 번째 판은 다시 받는다)
- 프리워밍 실패가 에러 상태를 세팅하지 않는다
- 프리워밍 중 시작을 누르면 중복 요청이 생기지 않는다

## 3. 시간대 배경

### 애셋

`~/Cloud/문서/작업/100. 기획/2026_일경험 완뚝/gfx/황령산 전망대_parts/main_bg/` — 6장,
전부 1920×1080. **해상도와 구도가 모두 동일**하게 맞춰져 있어 크로스페이드가 자연스럽다.

### 단계 구분

일출·일몰을 기준으로 6단계를 나눈다.

| 단계 | 파일 | 구간 |
|---|---|---|
| 새벽 | `city_dawn` | 일출 −60분 ~ 일출 |
| 아침 | `city_morning` | 일출 ~ 일출 +3시간 |
| 낮 | `city_day` | ~ 일몰 −90분 (요청서의 '오후' 포함) |
| 저녁 | `city_evening` | 일몰 ±90분 |
| 밤 | `city_night` | 일몰 +90분 ~ 23:00 |
| 심야 | `city_midnight` | 23:00 ~ 새벽 |

### 일출·일몰 표

**부산(35.1796°N, 129.0756°E) 기준 주차별 값을 상수 배열로 박는다.** 외부 API도 위치
권한도 쓰지 않는다 — 매장이 부산 고정이고, 오프라인에서도 동작해야 하며, 테스트 가능해야 한다.

NOAA 알고리즘으로 산출했고(주차별 수요일 대표값) 검증했다:

- 2026-01-01 일출 **07:33** — 부산 신년 일출로 널리 알려진 07:32와 일치
- 하지 05:11 / 19:43, 동지 07:30 / 17:17 — 부산의 알려진 범위와 일치

**생성 스크립트는 `docs/gen-daylight-table.py`에 이미 만들어뒀고, 아래가 그 출력이다.**
서브에이전트는 이 값을 그대로 쓸 것 — 다시 계산하지 말 것.

```ts
// 부산(35.18N, 129.08E) ISO 주차별 일출·일몰 (KST 분 단위, 자정 기준)
// docs/gen-daylight-table.py 로 생성. 연도 무관 — 매년 재사용한다.
// 검증: W01 일출 07:33 / 하지 무렵 05:10 / 동지 무렵 07:34
export const SUNRISE_MIN = [453, 454, 453, 451, 447, 442, 436, 429, 420, 412, 402, 392, 382, 372, 363, 353, 345, 336, 329, 323, 318, 314, 311, 310, 310, 311, 314, 317, 321, 326, 331, 336, 342, 347, 353, 358, 363, 368, 373, 378, 384, 389, 395, 402, 408, 415, 422, 429, 435, 441, 446, 450, 453];
export const SUNSET_MIN = [1042, 1048, 1054, 1061, 1068, 1075, 1082, 1089, 1096, 1102, 1108, 1114, 1120, 1125, 1131, 1136, 1142, 1148, 1154, 1159, 1165, 1170, 1175, 1178, 1181, 1183, 1183, 1182, 1180, 1176, 1171, 1165, 1158, 1150, 1142, 1132, 1122, 1112, 1102, 1092, 1082, 1072, 1064, 1056, 1048, 1043, 1038, 1035, 1033, 1033, 1034, 1037, 1041];
```

**53개다**(53주차 포함). 색인은 `week - 1`이며 방어적으로 클램프할 것.

**표는 연도와 무관하다.** 주차로만 색인하며 매년 그대로 재사용한다 — 해마다 다시
생성하지 말 것. 주차별 일출·일몰 차이는 연도 간 몇 분 수준이라 배경 전환 용도에는
영향이 없다.

> **ISO 주차는 53까지 있다.** 2026-01-01이 목요일이라 2026년은 **53주차가 존재한다**
> (2027년은 52까지). 표를 52개만 만들고 `TABLE[week - 1]`로 읽으면 연말에 `undefined`가
> 나와 **NaN 비교로 조용히 틀린 배경이 뜨거나 터진다.** 53개를 만들거나 색인을
> 클램프할 것(`Math.min(week, TABLE.length) - 1`). **53주차 케이스를 테스트에 넣을 것** —
> 이 저장소가 다른 가드 테스트를 두는 이유와 같은 "조용히 틀리는" 부류다.

> **주의: 이 값은 천문 계산이지 KASI 공식 발표표가 아니다.** KASI는 도시별 표를 HWP
> 첨부로만 제공해 대조하지 못했다. 분 단위 오차가 문제되는 용도가 아니므로(배경이
> 바뀌는 시점) 충분하다고 판단했다.

### 전환 연출

요청서: "이미지가 바뀌기로 한 시간대 즈음에 접속했을 때에는 **5초의 fade**"

해석이 갈리는 부분이라 **아래로 정한다**: 경계 부근(±N분)에 접속하면 이전 단계 이미지로
시작해 5초에 걸쳐 다음 단계로 크로스페이드한다. 경계에서 먼 시각이면 그냥 해당 이미지를
띄운다. 게임 중에 시간이 흘러 경계를 넘는 경우는 다루지 않는다 — 한 판이 짧고, 배경이
플레이 도중 바뀌면 오히려 산만하다.

### 배치

**`object-cover` + `object-position: center`** — 세로 화면에서는 좌우가 잘리고 가로
화면에서는 꽉 찬다. 원본 하나로 모든 뷰포트를 커버하는 반응형 원칙이다(2026-08-15 이란토).

- **뷰포트별로 이미지를 따로 준비하지 않는다.** 대응해야 할 화면비가 무한하다.
- 높이는 `dvh` 기준으로 잡는다. **`vh`를 쓰지 말 것**(AGENTS.md의 전용 절 참고).

### 주의

- **첫 화면은 밝은 회색 크롬(90s 데스크톱) 컨셉이다.** 배경 사진 위에 흰 문서 영역과
  베벨이 올라가므로 **대비가 죽지 않는지 실물로 확인**해야 한다. 특히 `city_midnight`
  같은 어두운 배경 위에서 텍스트 가독성이 유지되는지. 필요하면 반투명 오버레이를 깐다.
- 강제 다크모드는 이미 `darkreader-lock`으로 막혀 있다(AGENTS.md).
- **배경은 현재 시간대 1장만 받는다.** 6장을 다 받으면 용량 판단의 전제가 깨진다.

---

## 4. 애셋 파이프라인

`docs/build-intro-assets.sh`를 만든다(`build-sfx.sh`와 같은 방식 — 원본은 기획 폴더에,
변환본만 리포에).

- **배경 6장: 원본 1920×1080 그대로 복사한다.** 줄이지 않는다.
- 슬라이드 3장: 폭 **800** 상한 (비율 유지) + webp 재인코딩

### 배경을 줄이지 않는 이유

세로 화면에서 좌우가 잘리는 것을 **전제로** 하므로(위 `object-cover` 결정) 해상도 여유가
필요하다. 390×844 폰을 덮으려면 이미지 높이가 최소 844여야 하는데 1280×720으로 줄이면
**1.17배 확대되어 뿌옇게 된다.** DPR 2~3이면 더 심하다.

용량 부담도 크지 않다 — **배경은 현재 시간대 1장만 받는다.** 6장 합계는 1.2MB지만 방문자
한 명이 받는 것은 200KB 안팎이다(2026-08-15 이란토 판단: "그것조차 부담스러운 정도는 아니다").

**6장을 미리 다 받지 말 것.** 그 순간 이 판단의 전제가 깨진다.

원본 경로가 한글이고 공백이 있으므로 스크립트에서 인용에 주의할 것.

## 5. 작업 분할 (서브에이전트)

셋은 **파일이 거의 겹치지 않아** 병렬로 돌릴 수 있다.

| # | 작업 | 주요 파일 | 의존 |
|---|---|---|---|
| A | 애셋 파이프라인 | `docs/build-intro-assets.sh`, `public/images/**` | 없음 |
| B | 시간대 배경 | `app/lib/daylight.ts`(신규), `StartScreen.tsx` | A(파일명 규약만) |
| C | 로딩 읽을거리 | `PreloadScreen.tsx`, 로케일 4종 | A(파일명 규약만) |
| D | 데이터 프리워밍 | `preloadGame.ts`, `useGameProgress.ts`, `page.tsx` | 없음 |

- **A를 먼저 확정**한다(출력 경로·파일명). B·C는 그 규약만 알면 병렬 가능.
- **D는 완전히 독립**이므로 처음부터 병렬로 돌린다.
- B·C·D 모두 `StartScreen`/`page.tsx`를 스칠 수 있으므로 **충돌 지점을 미리 못박는다**:
  - D는 `page.tsx`의 프리워밍 훅 배선만
  - B는 `StartScreen`의 루트 `<div>` 배경만
  - C는 `PreloadScreen` 내부만

### 공통 준수 사항 (모든 서브에이전트에게 전달)

- `AGENTS.md`를 먼저 읽을 것. 특히 **`vh` 금지(`dvh` 사용)**, 픽셀 폰트 서브셋,
  로케일 폴백 순서.
- 새 한글 문구가 생기면 픽셀 폰트 재빌드 대상인지 확인.
- 테스트는 순수 로직만(`app/lib/*.test.ts`). 컴포넌트 테스트 인프라가 없다.
- `npm test`와 `npx tsc --noEmit`이 통과해야 한다.
