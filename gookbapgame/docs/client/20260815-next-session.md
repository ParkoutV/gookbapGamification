# 다음 세션 착수 목록 (2026-08-14 실기 플레이에서 나온 것)

이란토가 프로덕션에서 직접 플레이하다 발견한 UX 결함 2건. 둘 다 **비동기 응답을 기다리는
동안 화면이 아무 말도 하지 않는 것**이 원인이고, 처방도 같은 계열이다 — 응답을 기다리지
말고 화면부터 바꾼 뒤 내용물을 로딩 상태로 채운다.

`ROADMAP.md`와 별개 문서인 이유: 그쪽은 2026-08-05 회의에서 나온 기능 목록이고,
이건 그 뒤 실기에서 나온 결함이라 성격이 다르다.

## 1. 쿠폰 보관함이 늦게 열리고, 그 사이 누른 클릭이 전부 쌓인다

### 증상 (이란토 실기, 2026-08-14)
'내 쿠폰 보기'를 눌러도 바로 안 열려서 여러 번 눌렀더니, **다른 페이지로 이동한 뒤에도
보관함 창이 여러 번 떴다.** 눌린 횟수만큼 화면 전환이 큐에 쌓인 것.

### 원인
`app/page.tsx`의 `openMyCoupons`가 **조회를 끝낸 뒤에** 화면을 전환한다.

```js
const openMyCoupons = useCallback(async (returnTo = "start") => {
  setMyCouponsReturnPhase(returnTo);
  await refreshCoupons();     // ← 여기서 기다리는 동안 화면은 그대로다
  goToPhase("myCoupons");     // ← 응답이 와야 비로소 전환
}, [goToPhase, refreshCoupons]);
```

`refreshCoupons`는 `fetchMyCoupons` / `ensureWebCoupons` / `fetchWebCouponSettings`
**세 개를 병렬로** 부르고 전부 기다린다(`Promise.all`). 그중 `ensureWebCoupons`는 목록이
비어 있으면 발급 API까지 한 번 더 시도하므로 매장 네트워크에서는 더 느려질 수 있다.

버튼에 중복 클릭 가드가 없어서 누른 만큼 이 함수가 새로 돈다.

### 호출부는 세 곳이다 — 한 곳만 고치면 안 된다
- `app/page.tsx:320` 시작 화면(`onOpenMyCoupons={() => void openMyCoupons("start")}`)
- `app/page.tsx:434` 뽑기 거절 화면(`openMyCoupons("wheel")`, 2026-08-14 추가)
- `app/page.tsx:468` 오늘의 결과(`openMyCoupons("dailyResult")`)

세 곳 모두 같은 `openMyCoupons`를 부르므로 **거기 한 곳에서 막는 것이 맞다.**
버튼마다 `disabled`를 다는 방식은 세 곳에 흩어져 언젠가 하나가 빠진다.

### 이란토가 제시한 두 방향
1. **응답이 올 때까지 버튼을 한 번만 누를 수 있게** (중복 호출 차단)
2. **화면을 먼저 띄우고 내용물을 "불러오는 중..."으로** (낙관적 전환)

**2번을 권한다.** 1번만 하면 여전히 "눌렀는데 아무 일도 안 일어나는" 구간이 남는다 —
사용자가 여러 번 누른 이유가 바로 그것이었다. 2번이면 누른 즉시 화면이 바뀌므로
연타할 이유 자체가 사라진다. 다만 **2번을 해도 1번(가드)은 같이 두는 편이 안전하다** —
보관함이 열린 뒤 다른 경로로 다시 부를 여지가 남는다.

### 구현 시 확인할 것
- `MyCouponsScreen`에 로딩 상태가 **아직 없다.** 지금은 열릴 때 이미 데이터가 있다는
  전제라, 빈 배열이면 곧장 `coupon.empty`("아직 받은 쿠폰이 없어요.")를 띄운다.
  낙관적 전환으로 바꾸면 **로딩 중에 그 문구가 잘못 뜬다** — 조회 실패와 "정말 없음"을
  구분하라는 기존 원칙(`ranking.empty` 주석 참고)과 같은 함정이다.
- 로딩 문구 키가 필요하면 `ranking.loading`("불러오는 중...")과 같은 계열로 4개 로케일에
  추가할 것. 새 한글이 들어가면 픽셀 폰트 서브셋 재빌드 대상인지 확인
  (`bash docs/build-pixel-font.sh` — 다만 이 화면은 본문 폰트라 아마 불필요).
- `refreshCoupons`는 실패해도 예외를 던지지 않고 조용히 빈 값을 준다. 낙관적 전환에서는
  "로딩 끝났는데 비어 있음"과 "조회 실패"가 화면에서 같아 보이므로, 실패를 구분해서
  보여줄지 판단이 필요하다(랭킹은 `loadFailed`로 구분한다).

## 2. 랭킹 탭을 옮길 때마다 창 높이가 출렁인다

### 증상
탭 전환 → 데이터 오는 동안 창이 줄었다가, 목록이 채워지면 다시 늘어난다.

### 원인
`app/components/RankingScreen.tsx`의 상태별 렌더 높이가 서로 다르다.

| 상태 | 현재 렌더 | 높이 |
|---|---|---|
| 로딩(`!current`) | `<p className="py-8">불러오는 중...</p>` | 한 줄 + 패딩 |
| 실패 | `<p className="py-8">` | 한 줄 + 패딩 |
| 빈 목록 | `<p className="py-8">` | 한 줄 + 패딩 |
| 목록 있음 | 헤더 + **236px 고정 목록** | 고정 |

목록 쪽만 고정 높이(236px)를 갖고 나머지 세 상태는 한 줄짜리라, 그 차이만큼 창이 움직인다.

`loaded.period !== period`가 곧 "아직 안 온 것"이라 **탭을 옮길 때마다 반드시 이 구간을
지난다**(그 판단 근거는 그 파일 55~66행 주석에 있다 — `loading`을 별도 state로 두지 않은
이유가 적혀 있으니 그 구조는 유지할 것).

### 이란토가 제시한 두 방향
1. 높이를 고정하는 빈 페이지를 만든다
2. '불러오는 중'의 height 값을 고정한다

**둘은 사실 같은 처방이다** — 로딩·실패·빈 목록 세 상태를 목록과 같은 높이의 컨테이너로
감싸면 된다.

높이는 `RankingScreen.tsx:220`의 `<ol className="... h-[236px]">`에 **리터럴로 박혀
있다**(주석: "한 줄 20px + gap 4px × 9 = 236px"). 네 상태가 이 값을 공유해야 하므로
한 곳에 빼서 쓰는 편이 안전하다 — **목록 높이만 바꾸고 로딩 쪽을 안 고치면 다시
어긋난다.**

### 주의
- 목록의 236px은 "마지막 페이지가 10건 미만일 때 패널이 줄어 버튼이 위로 튀는 것"을
  막으려고 2026-08-13에 넣은 값이다. 그 근거를 지우지 말 것.
- 헤더 행(등수/닉네임/점수)도 목록이 있을 때만 렌더된다 — 높이를 맞출 때 이것까지
  포함해야 완전히 고정된다.
- 320px에서 검증할 것. 탭 4개가 '전체' 한 줄 + 기간 3개 구조라(2026-08-14) 탭 영역
  높이는 이미 고정이다.

## 검증 방법

두 건 다 **응답이 느릴 때만** 드러나므로 로컬에서 그냥 눌러서는 재현되지 않는다.

- 네트워크 스로틀링(Playwright/DevTools)으로 지연을 만들어 확인할 것.
- 보관함 쪽은 **연타**가 재현 조건이다 — 한 번만 누르면 증상이 안 보인다.
- 랭킹 쪽은 탭을 빠르게 옮기면서 창 높이(`getBoundingClientRect().height`)를 재면
  출렁임이 수치로 잡힌다.
