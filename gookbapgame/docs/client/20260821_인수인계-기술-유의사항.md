# 인수인계 — 기술 유의사항

작성: 2026-08-21 (`gookbapgame` 클라이언트)

권한 위임을 앞두고, **저장소 어디에도 적혀 있지 않아 다음 사람이 처음부터 헤맬 것들**만
남긴다. 코드의 설계 근거는 `AGENTS.md`에, 변경 경위는 커밋 메시지에 있다.

---

## 1. 환경변수는 각각 별개다

게임 쪽 Vercel에 저쪽(`gookbapanalyze`) API를 가리키는 변수가 **셋** 있다.

| 변수 | 대상 | 없거나 틀리면 |
|---|---|---|
| `GENERATE_UNIFIED_API_URL` | 이미지 합성 | 게임이 시작되지 않음 |
| `GATCHA_DRAW_API_URL` | 카드 뽑기 | 뽑기가 통째로 실패(폴백 없음) |
| `WEB_COUPON_ASSIGN_API_URL` | 온라인몰 쿠폰 발급 | 발급만 조용히 건너뜀 |

**"다른 기능이 되니 이 URL도 맞다"고 판단하지 말 것.** 하나만 틀려도 나머지는 멀쩡하다.
2026-08-21에 이 논증으로 후보를 배제했다가 반나절을 저쪽 코드 의심에 썼다.

**Vercel 환경변수는 바꾼 뒤 재배포해야 반영된다.**

발급 실패의 판별자는 게임 쪽 함수 로그 한 줄이다:
`[assignWebCoupon] 발급 실패(rejected=<T/F>): <error>`

---

## 2. 웹쿠폰은 한 참여자에게 두 장이 나갈 수 있다

**결함이 아니라 운영 설정의 귀결이다.** 배정 경로가 둘이고 같은 `web_coupons` 재고를 쓴다.

- **설문 보상**: `assign_web_coupon` RPC. 설문(phase 1) 최초 응답자에게 100% 확정.
- **가챠 당첨**: 저쪽 `draw/route.ts`가 `participant_id is null`인 행을 직접 집어 PATCH.
  쿠폰 효과의 `is_online_coupon`이 켜져 있고 그 구간 확률이 0이 아닐 때만 일어난다.

뽑기를 하려면 설문을 완료해야 하므로(서버가 `SURVEY_REQUIRED`로 검증), **뽑기를 한
사람은 전원 이미 설문 보상 1장을 받은 상태**다. 거기에 가챠 당첨이 겹치면 2장이 된다.

2026-08-21 실측: 뽑기 7판 중 2판(29%)에서 가챠가 온라인 쿠폰을 뽑아 **7명에게 9장**.

조정은 대시보드 **쿠폰 관리 → 확률 편집기**에서 한다(온라인 쿠폰은 목록 맨 위에 정렬).
**이 값은 운영 판단이며, 클라이언트는 어떤 확률에서도 올바르게 동작한다.**

주의 둘:
- 저쪽 `draw/route.ts`는 온라인 쿠폰을 `max_issuance`·`daily_max_issuance` 소진 판정에서
  **제외**한다. 확률이 있으면 재고와 무관하게 계속 뽑힌다.
- 대시보드의 게임 데이터 초기화는 배정된 `web_coupons` 행을 **행째 DELETE**한다.
  초기화할 때마다 재고가 영구히 준다.

---

## 3. `assign_web_coupon` RPC가 중복 발급을 막지 못한다

이미 쿠폰을 받은 participant로 다시 호출해도 `already_assigned: false`로 **새 코드를
준다**(2026-08-21 실측 2회). 필드가 있는 것을 보면 막으려는 의도는 있으나 작동하지 않는다.

클라이언트는 목록이 비어 있을 때만 호출하므로(`ensureWebCoupons`) 실사용에서는 잘
드러나지 않지만, 조회가 한 번 실패하면 재고가 샌다. **`gookbapanalyze` 쪽 사안이다.**

---

## 4. 설문이 생략되는 것은 정상이다

`enterSurveyFlow`가 `check_pending_survey` RPC로 미응답 문항을 묻고 **0건이면 곧장
뽑기로 보낸다.** 설문은 participant당 한 번뿐이고, 판정 권위는 서버(`survey_responses`)에
있다(2026-08-15에 localStorage에서 옮겼다).

**시크릿창에서 새 탭을 열면 세션이 이어져** 설문이 뜨지 않는다. 새 참여자로
시연·테스트하려면 **창을 완전히 닫고 다시 열 것.** 2026-08-21에 이것을 회귀로
오인할 뻔했다.

## 5. 배포본을 진단하는 법

- **게임은 전부 서버 액션이라 브라우저 네트워크 탭에 DB·API 호출이 보이지 않는다.**
  그래도 **서버 액션의 반환값은 직렬화되어 오므로**, Playwright로 POST 응답 본문을
  읽으면 `0:{...}\n1:{"ok":false}\n` 형태로 그대로 보인다.
  `ctx.cookies()`는 httpOnly 쿠키도 준다.
- **Supabase 로그가 가장 강력하다.** 요청 경로와 순서만으로 어느 분기를 탔는지 읽힌다 —
  2026-08-21 조사의 결정적 증거가 전부 여기서 나왔다.
- **`game.1953bros.com`은 Vercel Attack Challenge Mode가 켜져 있다.** curl은 429를 받는다
  (`x-vercel-mitigated: challenge`). 실브라우저(Playwright 등)는 통과한다.
- 대시보드 배포: `https://1953bros-dashboard.kro.kr`

## 6. 아직 확인되지 않은 것

- **온라인몰 쿠폰 카드의 '이미지로 저장' 결과물.** 화면 표시는 확인됐으나, canvas의
  `qrSvg: null` 경로는 프로덕션에서 한 번도 실행된 적이 없던 분기다(꽝 카드는 저장
  버튼 자체가 없었다). 저장된 PNG를 아직 아무도 보지 않았다.
- **`useGameProgress`의 `totalWrongTouches` / `comboBankedScore`**: setter만 호출되고
  값은 어디서도 읽지 않는다. 기능이 반쯤 걷힌 흔적으로 보인다(lint warning).
- **`npm run lint`는 warning 14건이 남아 있다**(에러 0). 13건은 게임 애셋에 대한
  `<img>` → `next/image` 권고라 그대로 두었다. **lint 실패는 배포를 막지 않는다** —
  Vercel Deployment Checks에서 실패해도 배포는 진행된다.
