**확정일** 2026-08-13 (이란토 확인)
**범위** 랭킹 페이지 — daily / weekly / monthly / total 탭

## 1. 데이터 출처

`supabase.from("ranking_view").select("*")` — RPC가 아니라 뷰 직접 조회다(analyze/AGENTS.md:471).

반환 컬럼: `nickname_first`(jsonb), `nickname_last`(jsonb), `nickname_number`, `best_score`, `gookbap_score`, `joined_time`.

### 기간 필터를 서버로 내려보낸다 — 행 잘림이 조용히 랭킹을 틀리게 만든다

뷰는 **플레이 한 번당 한 행**이 쌓인다(샘플에서 12명이 51행). 그리고 **PostgREST에는 응답 행수 상한이 있다** — 상한에 걸리면 오류 없이 앞부분만 돌아온다. 닉네임당 최고점을 구하려면 **모든 행이 필요하므로**, 잘린 응답으로 계산한 랭킹은 조용히 틀린다.

- daily / weekly / monthly는 `.gte("joined_time", boundaryIso)`로 서버에서 거른다. 공짜로 해결된다(경계 값은 아래 3절에서 만든다).
- `total`은 그럴 수 없다. **상한에 걸렸는지 감지해서 화면에 알린다.** 페이지네이션(`.range()`)으로 전부 받아오거나, 최소한 "일부만 표시됨"을 표시할 것. 조용히 자르지 말 것 — 표시 상한과 같은 규칙이다.
- **상한 값을 추측하지 말고 실제로 확인할 것.** 로컬에 행을 넉넉히 넣고 `select("*")` 결과 길이와 `select count(*)`를 비교하면 드러난다.

### 점수는 `gookbap_score`를 쓴다

**`best_score`를 쓰지 말 것**(2026-08-13, 이란토 확정). 실측 확인 결과:

- 이란토가 뜬 샘플 50행에서 **`best_score`가 전부 0**이고 실제 점수는 `gookbap_score`에만 있다(최대 1953).
- 원인은 클라이언트가 `gookbap_score`만 insert하기 때문이다(`actions.ts`의 `submitGameScore`). `best_score`는 NOT NULL이라 기본값 0으로 들어간다.
- analyze/AGENTS.md:210-211은 둘을 다른 개념으로 정의하지만(`best_score` = 최고 점수, `gookbap_score` = 국밥 재화 점수), **클라이언트에는 점수가 하나뿐이고**(`breakdown.total`) 이란토가 `best_score`는 안 쓴다고 확정했다.

`submitGameScore`를 고쳐 `best_score`도 채우지 말 것 — 재화 집계를 오염시킬 수 있고, 이란토가 안 쓴다고 한 컬럼이다.

### `participant_id`는 쓰지 않는다 — 쓸 수도 없다

`ranking_view`에 그 컬럼이 **아예 없다**(뷰가 의도적으로 제외했다). 이란토 설명: 그 값이 전부 노출되면 **남의 쿠폰을 가로챌 취약점**이 열린다.

그래서 사람 단위 집계는 닉네임으로 한다 — 세션 ID당 닉네임 조합이 하나로 고정되므로 사람 단위 키로 성립한다(2026-08-13, 이란토).

## 2. 사람 단위로 묶기 — 닉네임당 최고점 한 줄

한 사람이 여러 번 플레이한 기록이 **필터링 없이 전부** 온다(analyze/AGENTS.md:366). 샘플에서 12명이 51행을 만들었고 한 명은 34회였다. 그대로 나열하면 상위권이 한 사람으로 도배된다.

닉네임당 **가장 높은 `gookbap_score` 한 줄만** 남긴다.

### 그룹 키에 표시 문자열을 쓰지 말 것 — 이게 이 작업의 핵심 함정이다

`formatNickname`의 결과를 키로 쓰면 **두 가지가 동시에 깨진다**:

1. **로케일마다 문자열이 달라진다.** "든든한 국밥 #0023"과 "Hearty Gookbap #0023"이 같은 사람인데 언어를 토글하면 그룹이 다시 계산된다.
2. **더 나쁜 것 — 서로 다른 사람이 같은 키가 될 수 있다.** `formatNickname`은 두 단어가 모두 해당 로케일로 번역돼 있을 때만 그 언어를 쓰고, 하나라도 비면 **통째로 한국어로 떨어뜨린다**(`nicknameParts.ts:51-58`). 영어 화면에서 번역이 덜 된 두 사람이 같은 한국어 문자열로 수렴할 수 있다.

키는 **로케일과 무관한 값**으로 만든다: `nickname_first.ko` + `nickname_last.ko` + `nickname_number`. 번호가 UNIQUE 제약에 포함되므로(analyze/AGENTS.md:173) 같은 단어 조합이라도 사람이 갈린다.

`nickname_number`가 null인 행이 있을 수 있다(`NicknameParts.number`가 nullable이다). null은 빈 문자열이 아니라 **고유한 자리표시자**로 취급해 서로 다른 무번호 참가자가 합쳐지지 않게 한다.

### 동점자

`joined_time`이 **이른** 쪽이 위다. 명세가 이 컬럼을 "동점자 발생 시 랭킹을 판가름하기 위해 정렬 시 참조되는 시간"으로 정의한다(analyze/AGENTS.md:367) — 먼저 도달한 사람이 이긴다.

**같은 규칙을 그룹 안에서도 적용한다.** 한 닉네임의 두 기록이 점수까지 같으면 `joined_time`이 이른 쪽을 남긴다. 그러지 않으면 그룹 대표가 순회 순서에 따라 달라져 위의 동점 정렬이 흔들린다.

## 3. 기간 필터 — 달력 기준, KST

| 탭 | 범위 |
|---|---|
| daily | KST 오늘 00:00 ~ |
| weekly | KST 이번 주 월요일 00:00 ~ |
| monthly | KST 이번 달 1일 00:00 ~ |
| total | 전체 |

**롤링 윈도우가 아니다**(이란토 확정). "이번 주 1위"가 집계하기도 쿠폰 지급하기도 직관적이어서 매장 운영에 맞는다.

### KST 경계 계산 — `couponRemaining.ts`의 `kstDayStart`를 재사용하지 말 것

같은 파일에 KST 날짜를 다루는 함수가 있지만 **용도가 다르고, 그대로 쓰면 9시간 구멍이 뚫린다.**

`kstDayStart`는 `Date.parse(ymd + "T00:00:00Z")`를 돌려준다 — 날짜 차를 빼기 위한 **비교용 키**이고 실제 시점이 아니다. KST 오늘 00:00은 **UTC 어제 15:00**인데 `kstDayStart`는 UTC 오늘 00:00(= KST 09:00)을 준다. 이 값으로 `joined_time`을 걸러내면 **KST 00:00~09:00에 플레이한 기록이 통째로 사라지고, 오류는 나지 않는다.**

경계는 **실제 시점(instant)으로** 만들어야 한다:

1. KST 날짜 문자열을 얻는다 — `toLocaleDateString("en-CA", { timeZone: "Asia/Seoul" })` (ISO 형식 YYYY-MM-DD를 준다).
2. 그 날짜에 오프셋을 붙여 시점으로 만든다 — `new Date(`${ymd}T00:00:00+09:00`)`.

`+09:00`을 `Z`로 쓰지 말 것 — 그것이 위의 9시간 구멍이다.

주 시작을 월요일로 잡을 때 `Date.getDay()`는 일요일이 0이므로 그대로 빼면 안 된다. `(day + 6) % 7`이 월요일 기준 오프셋이다. **요일도 KST 기준으로 구해야 한다** — 기기 시간대의 `getDay()`는 경계 근처에서 하루 어긋난다.

경계 계산은 순수 함수로 빼서 테스트한다 — 월요일 당일, 일요일(주의 마지막 날), 1일, 월말, 연말 경계를 각각 확인할 것. **KST 00:00~09:00 구간을 반드시 테스트에 포함할 것**(위 함정이 정확히 그 구간이다).

### 레이아웃

- 다른 화면과 같은 `PixelPanel size="card"` + `max-w-sm`.
- 탭 4개를 가로로. 좁은 화면(320px)에서 넘치지 않아야 한다 — 실측할 것.
- 순위 목록: 등수 · 닉네임 · 점수. 닉네임은 `formatNickname`으로 렌더한다(표시는 로케일을 따라야 한다 — 키와 다르다).

- 기록이 없는 탭(예: 오늘 아무도 안 함)은 빈 목록 안내 문구를 띄운다. 로딩 실패와 구분해야 한다 — 설문 조회에서 같은 교훈이 있다(`surveyFetchResult.ts`).

### 내 기록 강조는 하지 않는다

## 5. 로케일

`ko` / `en` / `ja` 세 파일 모두. 탭 이름 4개, 빈 목록 안내, 조회 실패 안내, 표시 상한 안내, 순위·점수 레이블.

**비ASCII 구분자를 쓰지 말 것.** en dash(–), 물결(～) 등은 픽셀 폰트 서브셋 재빌드를 요구하고 빠뜨리면 두부가 된다(2026-08-13에 en 로케일에서 실제로 발생). 새 문자를 넣었으면 `python3`로 서브셋 포함 여부를 확인할 것:

```python
from fontTools.ttLib import TTFont
cmap = TTFont('public/fonts/Galmuri11.woff2').getBestCmap()
print([c for c in set('새 문자들') if ord(c) not in cmap])
```

## 7. 로컬 검증

`ranking_view`가 로컬에 없다. `docs/test-db/schema.sql`에 뷰를 만들고 시드를 넣어야 **실제 컴포넌트로 확인할 수 있다.**

**스텁은 반환 컬럼 모양만 맞추면 된다.** 프로덕션의 `participants` → `nickname_presets` 조인을 재현하려 하지 말 것 — 로컬에 그 테이블들이 없거나 형태가 달라 시간만 버린다. 평범한 시드 테이블 위에 뷰를 올려 여섯 컬럼을 내놓으면 충분하다. 방금 검증한 `get_my_coupons` 스텁과 같은 방침이다(그쪽 주석 참고).

이 저장소는 손으로 조립한 DOM만 보고 넘겼다가 실제 상호작용 버그를 놓친 전례가 있다(2026-08-13 앨범 blob 오염). 시드에는 반드시 포함할 것:

- 같은 닉네임의 여러 기록(최고점 한 줄로 줄어드는지)
- 번호가 null인 행 2건 이상(합쳐지지 않는지)
- 동점 + `joined_time` 차이
- 기간 경계에 걸친 행(오늘 / 이번 주 / 지난달 / 작년)
- 번역이 한국어만 있는 프리셋(폴백이 그룹핑을 깨지 않는지)

**시드 날짜는 `now()` 기준 상대값으로 쓸 것.** 고정 문자열은 며칠 뒤 다시 부으면 구간이 달라진다. KST 경계를 만들 때 `current_date at time zone 'Asia/Seoul'`을 쓰면 하루 밀린다 — `docs/test-db/seed.sql`의 `seed_kst_end_of_day` 주석 참고.

`ranking_view`는 뷰이므로 `grant select ... to anon`이 필요하다. schema.sql의 GRANT 위치 함정(테이블 생성보다 앞서면 죽는다)도 같은 파일 주석에 있다.
