# 닉네임 다국어 대응 요청 — 배정 API 응답 형식

작성: 2026-08-12 / gookbapgame(게임 클라이언트) → gookbapanalyze(대시보드·API)

## 요약

영문·일본어 환경에서도 닉네임이 한국어로만 표시되는 문제입니다. 원인이 **두 갈래**인데,
한쪽은 게임 클라이언트 잘못이라 저희가 고칩니다. 다른 한쪽은 **배정 API 응답 형식** 때문에
저희 쪽만으로는 해결할 수 없어 요청드립니다.

| 경로 | 시점 | 원인 | 담당 |
|---|---|---|---|
| 조회 (`get_participant`) | 재방문 | 게임 클라이언트가 `ko`만 읽고 있었음 | **저희가 수정** |
| 배정 (`/api/nickname/assign`) | 첫 방문 | API가 조립된 한국어 문자열만 반환 | **요청 대상** |

## 1. 현재 상태

### 조회 경로 — DB는 다국어를 주고 있는데 저희가 버리고 있었습니다

`get_participant` RPC는 명세대로 jsonb 맵을 돌려줍니다.

```json
"nickname_first": { "ko": "든든한", "en": "Hearty" },
"nickname_last":  { "ko": "국밥",   "en": "Gookbap" },
"nickname_number": "0023"
```

그런데 게임 클라이언트(`app/lib/existingNickname.ts`)가 `ko` 키만 강제로 꺼내
쓰고 있었습니다.

```ts
const KO = "ko";
function pickKorean(value: unknown): string | null {
  const text = (value as NameMap)[KO];   // 로케일 무시
  ...
}
```

**이 부분은 저희 쪽 문제이므로 저희가 수정합니다.** 지적해 주셔서 감사합니다.

### 배정 경로 — 응답에 언어를 고를 여지가 없습니다

`POST /api/nickname/assign`의 응답은 다음과 같습니다(AGENTS.md 명세 기준, 실제 코드도 동일).

```json
{
  "success": true,
  "nickname": "든든한 국밥 #0023",
  "first_id": "uuid-first",
  "last_id":  "uuid-last",
  "number":   "0023"
}
```

`nickname`이 **이미 한국어로 조립된 문자열 하나**라, 게임 클라이언트가 영문·일본어 환경에서
쓸 수 있는 데이터가 없습니다. 첫 방문 유저는 어떤 언어를 선택했든 한국어 닉네임을 받게 됩니다.

DB에는 다국어 데이터가 있고(`nickname_presets.text`가 jsonb), 응답이 `first_id`/`last_id`를
함께 주는 것으로 보아 조립 전 재료도 서버가 들고 있는 것으로 이해했습니다.

## 2. 요청 사항

**배정 API도 `get_participant`와 같은 형태로 jsonb 맵을 반환해 주실 수 있을까요.**

```json
{
  "success": true,
  "nickname": "든든한 국밥 #0023",          // 기존 필드 유지 (하위 호환)
  "nickname_first": { "ko": "든든한", "en": "Hearty", "ja": "..." },
  "nickname_last":  { "ko": "국밥",   "en": "Gookbap", "ja": "..." },
  "first_id": "uuid-first",
  "last_id":  "uuid-last",
  "number":   "0023"
}
```

- **기존 `nickname` 필드는 그대로 두시는 편이 안전합니다.** 저희 외에 쓰는 곳이 있을 수 있고,
  필드 추가만으로 끝나므로 기존 호출부가 깨지지 않습니다.
- 조립(`first + 공백 + last + NBSP + #number`)은 지금처럼 게임 클라이언트가 하겠습니다.
  조회 경로에서 이미 그렇게 하고 있어 두 경로의 처리가 통일됩니다.
- 언어 코드는 `supported_languages`에 등록된 활성 언어를 그대로 주시면 됩니다.
  저희 쪽에서 `locale → ko → "—"` 순으로 폴백하므로, 특정 언어가 비어 있어도 안전합니다.

### 대안: 로케일 파라미터 방식은 권하지 않습니다

요청 시 `locale`을 받아 해당 언어 문자열을 조립해 주시는 방법도 있지만, 게임 화면에는
언어 토글이 있어 **접속 후에도 언어가 바뀝니다.** 그때마다 API를 다시 부를 수는 없어서,
맵을 통째로 받아 두고 화면에서 고르는 편이 맞습니다. 설문·쿠폰 등 다른 다국어 데이터도
모두 그렇게 처리하고 있습니다.

## 3. 저희 쪽 대응 계획

요청이 반영되기 전까지도 게임이 멈추지 않도록, 다음 순서로 진행할 예정입니다.

1. **조회 경로 수정** — `pickKorean`을 걷어내고 기존 헬퍼(`resolveLocalizedName`)를 씁니다.
   `locale → ko → "—"` 폴백이 이미 들어 있어 번역이 비어 있는 언어는 한국어로 표시됩니다.
   → 재방문 유저는 이 시점에 해결됩니다.
2. **닉네임을 문자열이 아니라 맵으로 들고 다니도록 변경** — 지금은 서버 액션이 문자열로
   확정해서 넘기는데, 그러면 접속 후 언어를 바꿔도 닉네임이 그대로입니다. 맵을 넘기고
   화면에서 로케일로 고르도록 바꿉니다.
3. **배정 경로 임시 우회** — 배정 성공 직후 `get_participant`를 한 번 더 호출해 맵을
   가져오는 방법을 검토 중입니다(첫 방문에만 왕복 1회 추가). 다만 **배정 직후 해당 행이
   즉시 조회되는지 확인이 필요**해서, 이 부분은 아래 질문과 함께 여쭙습니다.

**요청이 반영되면 3번은 걷어내고 배정 응답의 맵을 그대로 쓰겠습니다.** 1·2번은 그대로
유효하며, 그쪽에서 번역 데이터가 채워지는 즉시 게임 화면에 자동으로 반영됩니다.

## 4. 질문

1. `assign_random_nickname` RPC 직후에 `get_participant`를 호출하면 방금 배정된 닉네임이
   **바로 조회되나요?** (3번 우회안이 성립하는지 판단하는 데 필요합니다. 안 된다면 첫 방문
   대응은 2번 요청이 반영될 때까지 보류하겠습니다.)
2. 현재 진행 중인 **대시보드 자동 번역(빈 칸 기계 번역 채우기)** 작업이 `nickname_presets.text`도
   대상에 포함하시는지요. 포함된다면 저희는 별도 대응 없이 그대로 반영됩니다.
3. 지금 `nickname_presets.text`에 `en`·`ja` 값이 실제로 들어 있는 비율이 어느 정도인지
   알 수 있을까요. 비어 있는 항목이 많다면 저희 폴백(→ 한국어)이 자주 걸릴 텐데, 그 경우
   한 닉네임 안에서 앞말은 영어, 뒷말은 한국어로 섞여 보일 수 있어 표시 정책을
   따로 정하는 편이 나을 수 있습니다(예: 한 언어라도 비면 통째로 한국어로).

## 참고

- 게임 클라이언트에서 닉네임을 렌더하는 화면: 시작 화면(환영 문구), 오늘의 결과(닉네임 표시)
- 랭킹 화면은 아직 구현 전이라, `ranking_view`의 `nickname_first`/`nickname_last`(jsonb)도
  같은 방식으로 처리할 예정입니다.
- 로컬 폴백(`NICKNAME_ASSIGN_API_URL` 미설정 시 게임이 자체 생성하는 닉네임)은 개발·장애
  경로라 한국어 전용으로 남깁니다.
