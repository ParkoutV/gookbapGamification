## 1. 힌트 횟수 — 3회, 게임 전체 기준

`HINT_LIMIT_PER_GAME = 3`을 `app/lib/stageConfig.ts`에 둔다(`WRONG_TOUCH_LIMIT_PER_LEVEL`과 같은 자리).

### 상태를 어디에 두는가 — 여기서 틀리면 조용히 망한다

**`hintsUsed`는 `useGameProgress`에 둔다. `GameScreen`에 두면 안 된다.**

`GameScreen`은 **단계마다 리마운트된다**(`page.tsx`의 `key`, `GameScreen.tsx:27-35` 주석 참고). 거기에 카운터를 두면 "게임당 3회"가 아니라 "**단계당 3회**"가 되고, 설문도 매 단계 뜬다. 단계 하나만 열어보는 테스트는 이 버그를 통과시킨다.

- `hintsUsed` (number): `startGame`과 `resetToStart` 양쪽에서 0으로 리셋. 다른 카운터(`totalWrongTouches` 등)가 리셋되는 자리에 나란히 넣는다.
- `hintSurveyShownRef` (boolean ref): 이 판에서 설문을 이미 띄웠는지. 같은 두 곳에서 false로 리셋.
- `consumeHint()`: `hintsUsed`를 1 올린다. 훅에서 내보내 `GameScreen`이 호출.
- `hintsRemaining = HINT_LIMIT_PER_GAME - hintsUsed`를 반환값에 포함.

`isHintOpen`은 지금처럼 `GameScreen`의 로컬 state로 남긴다 — 단계가 바뀌면 닫히는 게 맞는 동작이다.

### 소모 시점

**'?' 버튼을 눌러 클립보드가 열리는 순간 1회 차감.** 단, 아래 설문 분기에서는 **설문에 응답한 시점**이다.

### '?'는 토글이 아니다 — 열기 전용

**`GameScreen.tsx:434`의 `setIsHintOpen((prev) => !prev)`를 열기 전용으로 바꾼다.** 열려 있는 동안 '?'를 다시 눌러도 닫히지 않는다. 닫고 다시 열면 1회가 더 나가므로, 토글은 곧 실수로 회수를 잃는 경로다.

**클립보드에서 바깥 탭 닫기를 제거한다**(`HintClipboard.tsx:28`의 스크림 `onClick`). 게임판 위 오버레이라 손가락이 빗나가기 쉽다. 종이 오른쪽 상단의 명시적인 ✖ 버튼과 Escape 키만 남긴다.

**설문 오버레이는 반대다 — 바깥 탭 닫기를 유지한다.** 그쪽은 닫아도 차감이 없으므로(아래) 쉽게 빠져나갈 수 있어야 한다. **이 차이 때문에 두 오버레이가 닫기 핸들러를 공유해서는 안 된다.**

차감하지 않는 경우:
- **설문에 응답하지 않고 닫은 경우** (이란토 확정). 설문 오버레이를 바깥 탭이나 닫기로 그냥 지운 것이므로 힌트를 받지 못했다 → 차감 없음.
- **강제 닫힘** — 단계 클리어(`GameScreen.tsx:102`)와 오답 한도 도달(`GameScreen.tsx:144`)에서 코드가 `setIsHintOpen(false)`를 부른다. 플레이어 의사가 아니므로 차감·환불 모두 없다(이미 열릴 때 차감됐고 그대로 둔다).
- `hintsRemaining === 0`이면 '?' 버튼을 `disabled`로 둔다. 눌러도 아무 일도 없다.

### 타이머

**설문 오버레이가 떠 있는 동안에도 전역 300초 타이머는 계속 흐른다**(이란토 확정). 일시정지 로직을 넣지 않는다. 문항이 단일 선택 탭 하나라 부담이 크지 않다.

## 2. 잔여 횟수 표시 — '?' 아이콘 반대편 3칸

게임 화면 가운데 열(`GameScreen.tsx:422~465`)은 위에서 아래로 `?` 버튼 → 시간 게이지 → 남은 초다. 힌트 칸 3개를 **`?` 버튼보다 앞(위)에** 넣는다 — "second gauge의 반대편"이라는 이란토 지시다.

- 시간 게이지의 칸 렌더 방식을 그대로 쓴다(같은 체계로 보여야 한다).
- **`time-gauge--warn` / `time-gauge--last` 클래스를 물려주지 말 것.** 남은 힌트 1개에서 빨갛게 깜빡이면 시간 경고로 오독된다.
- 가로 배치(`md:flex-col`)와 세로 배치 양쪽에서 게이지가 `flex-1 md:flex-none`이므로, 힌트 칸에는 `shrink-0`을 준다(안 주면 좁은 화면에서 눌린다).
- `role="img"` + `aria-label`로 잔여 횟수를 읽어준다. 오답 인디케이터(`GameScreen.tsx:498~504`)와 같은 방식.

## 3. phase 0 설문 — 게임당 최초 1회

### 트리거

한 판에서 **'?'를 처음 누른 시점**. `hintSurveyShownRef`가 false일 때만.

두 번째·세 번째 힌트는 **설문 없이 곧바로 클립보드**가 뜨고 그 지점에서 차감한다(이란토 확정).

### 문항을 고르는 방법

**클라이언트는 응답 횟수를 계산하지 않는다**(이란토 확정 — DB가 세션별 중복 참여를 가려낸다).

**호출은 두 번이다. `check_pending_survey`는 `question_id`만 돌려주므로 그것만으로는 화면을 그릴 수 없다**(analyze/AGENTS.md:414-424의 반환 예시 참고 — 문항 텍스트·선택지가 없다).

1. `fetchSurveyQuestions(0)` → phase 0 문항 **전체 행**(텍스트·선택지 포함).
2. `check_pending_survey({ p_survey_phase: 0, p_participant_id, p_track_id: null })` → 아직 답하지 않은 `question_id` 목록. **`p_track_id`는 null을 넘긴다** — track_id는 phase 2에서만 의미가 있다(analyze/AGENTS.md:413). 기존 코드에서 track을 찾아 헤맬 필요 없다.
3. 1번 행들을 2번 id 목록으로 걸러낸다. **교집합이 비어 있지 않으면 그중 무작위 1건.**
4. 교집합이 비면(전부 응답함) **1번 전체에서 무작위 1건** — 재탕. phase 0은 중복 응답 허용이므로 서버에서 막히지 않는다(analyze/AGENTS.md의 `trg_enforce_unique_survey_response_phase_1_2`는 phase 1·2만 대상).
5. `order_index`는 **정렬 순서일 뿐 우선순위가 아니다.** 무작위가 기본이다.

**`record_optional_survey_shown`은 호출하지 않는다.** 그것은 선택 문항(`is_required = false`)의 1회 노출 기록용이고, phase 0 문항은 전부 `is_required = true`다. 지금 부르면 오히려 다음 조회에서 문항이 제외돼 "다 응답했어도 재탕한다"는 요구와 충돌한다.

### 액션

`fetchSurveyQuestions`에 **phase 인자를 추가**한다(기본값 1로 두어 기존 호출부를 건드리지 않는다). 형제 함수를 새로 만들지 말 것 — `is_active`를 `= true`가 아니라 `not is false`로 거르는 등 이미 검증된 함정 처리가 그 안에 있다(`actions.ts:517-521`).

`check_pending_survey`용 액션을 하나 추가한다. `p_track_id`는 기존 코드가 track을 어떻게 들고 있는지 확인해 그대로 넘긴다.

### 실패는 전부 조용히 힌트 허용

**DB가 어떻게 실패하든 플레이어는 힌트를 받는다.** 힌트를 잃는 쪽이 훨씬 나쁘다.

- 문항 조회 실패 / 문항 0건 → 설문을 건너뛰고 곧바로 클립보드. **이때도 1회 차감한다** — 힌트를 실제로 받았으므로 공짜가 아니다. `hintSurveyShownRef`는 true로 세운다(같은 판에서 재시도하지 않는다).
- `check_pending_survey` 실패 → 설문을 포기하지 않는다. phase 0 전체에서 무작위로 떨어진다(위 4번과 같은 경로).
- **응답 제출 실패 → 화면에 아무것도 표시하지 않고 그대로 힌트를 준다**(이란토 지시: fallback blank). 제출 결과를 **await하지 않고** 클립보드를 연다. `submitSurveyResponses`의 `ok: false`를 절대 화면에 노출하지 말 것 — 쿠폰 경로(`useCouponFlow`)는 이 값을 에러 메시지로 띄우는데, 힌트 경로는 무시해야 한다.

### 화면

기존 `SurveyScreen`을 재사용하지 않는다 — 그쪽은 문항 전체를 받는 **전체 화면 패널**이고 게임 중에는 오버레이여야 한다. 문항 1건 · 단일 선택 전용의 작은 오버레이를 새로 만든다. `HintClipboard`와 같은 `--scrim` 배경 위 `PixelPanel`.

**새로 만드는 것은 화면뿐이다.** 제출은 기존 `submitSurveyResponses(questions, answers)`를 그대로 쓴다 — `buildSurveyResponseRows`가 type 0 문항을 이미 올바르게 처리한다(`answer_data`를 배열이 아니라 맨숫자로 넣는다, `surveyAnswers.ts:52-56`). insert 코드를 새로 쓰지 말 것.

응답을 제출하는 즉시 오버레이가 닫히고 클립보드가 뜬다. 응답 없이 닫으면 클립보드도 뜨지 않고 차감도 없다.

## 4. 가림 연출 — 감열지 인쇄 소실

무작위 문항 **1개**의 이름을 가린다.

**글자를 아예 렌더하지 않고 가토(`░░░░` 등)로 대체한다.** blur나 검은 사각형은 정답 문자열이 DOM과 접근성 트리에 그대로 남아 개발자도구·스크린리더로 읽힌다. 안 그리면 새어나갈 것이 없고 코드도 짧다. 모노스페이스·감열지 컨셉과도 맞아떨어진다.

**줄은 반드시 남긴다.** `HintClipboard`는 "줄 수 == 차이 슬롯 수"를 지키고 있다(`HintClipboard.tsx:7`, `localizedName.ts:9-10` 주석). 줄이 사라지면 플레이어가 문제를 다 찾은 것으로 착각한다. 가리는 것은 글자뿐이다.

**가릴 인덱스는 한 번 뽑아서 고정한다.** 열 때마다 다시 뽑으면 클립보드를 여닫는 것만으로 전부 드러난다. 다만 '?' 누를 때마다 차감되므로 이 노출 비용은 이미 3회로 제한돼 있다 — 그래도 같은 힌트를 다시 열었을 때 같은 칸이 가려져 있어야 일관돼 보인다.

`aria-label`도 가려진 줄은 "가려짐"에 해당하는 문구로 바꾼다(정답을 읽어주면 안 된다). 로케일 3종에 키를 추가한다.

## 5. 로케일

`ko` / `en` / `ja` 세 파일에 모두 추가한다. 하나만 빠져도 그 언어에서 키 문자열이 그대로 노출된다.

필요한 키(이름은 기존 `game.hint*` 계열을 따를 것):
- 잔여 힌트 `aria-label`
- 가려진 줄의 대체 `aria-label`
- 설문 오버레이 제목·안내
- 힌트 소진 상태 안내(버튼 `aria-label` 또는 툴팁)

**비ASCII 구분자를 쓰지 말 것.** en dash(–), 물결(～) 등을 넣으면 픽셀 폰트 서브셋 재빌드가 필요해지고 빠뜨리면 두부가 된다(2026-08-13에 en 로케일에서 실제로 발생). 가토 문자(`░`)는 **로케일 파일이 아니라 소스에 하드코딩**하고, 픽셀 폰트가 아닌 본문 폰트(`monospace`)로 렌더되는 자리인지 확인할 것 — `HintClipboard`는 `fontFamily: "monospace"`이므로 서브셋과 무관하다.

## 6. 테스트

순수 함수로 뺄 수 있는 것만 `node:test`로 검증한다(기존 223건과 같은 방식, `--experimental-strip-types`).

- 가릴 인덱스 선택과 가림 적용: 줄 수가 보존되는가, 가려진 줄이 정확히 1개인가, 슬롯이 1개일 때도 동작하는가(그 경우 전부 가려진다 — 의도된 것인지 확인 필요).
- 문항 선택: pending 목록이 있으면 그중에서, 비어 있으면 전체에서. 전체도 비어 있으면 null(→ 설문 건너뜀).
- 힌트 잔여 칸 렌더: `resolveIndicatorCells`를 재사용할 수 있으면 새 함수를 만들지 말 것.

**카운터가 `useGameProgress`에 있다는 사실은 단위 테스트로 잡히지 않는다.** 구현 후 실제로 2단계 이상 플레이해서 힌트가 단계 넘어도 누적되는지 확인할 것.

## 7. 차이 슬롯이 1~2개인 단계

`STAGE_CONFIG`의 `diffCount`는 5·5·5·5·5·5·7이지만 **실제 출제 개수는 이미지별 `questions_count`로 유동적이다**(`stageConfig.ts:65-67`). 슬롯이 1개인 단계가 나올 수 있다.

**슬롯이 2개 이하인 단계에서는 가림을 적용하지 않는다.** 1개면 전부 가려져 힌트가 완전히 무의미해지고, 2개면 절반이라 힌트 값이 과하게 떨어진다. 3개 이상에서만 1개를 가린다.

이 경계는 순수 함수로 빼서 테스트한다(슬롯 1·2·3개 각각).
